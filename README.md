## 1. Getting Started

There are different ways to access the walkthroughs.

### 1.1. Direct Web Access

#### 1.1.1. Official Website

For an interactive GUI with search filters, chapter navigation, and progress tracking, visit the [Simple Game Solutions Website](https://amigamaster.github.io/Simple-Game-Solutions).

#### 1.1.2. GitHub Repository

Browse the files directly in the [solutions](https://github.com/AmigaMaster/Simple-Game-Solutions/tree/master/solutions) folder here on GitHub.

### 1.2. Download

You can always download the latest version as a [ZIP file](https://github.com/AmigaMaster/Simple-Game-Solutions/archive/master.zip)

### 1.3. Clone

You can clone this repository to your local machine using the following link:

``` Text
https://github.com/AmigaMaster/Simple-Game-Solutions.git
```

#### 1.3.1. Windows

On Windows, we recommend using TortoiseGit, which integrates into the Windows graphical user interface:

1. Download and install Git for Windows: [https://gitforwindows.org](https://gitforwindows.org)

2. Download and install TortoiseGit: [https://tortoisegit.org](https://tortoisegit.org)

3. Right-click inside any folder and select `Git Clone...`  

4. Paste the repository URL into the URL field: `https://github.com/AmigaMaster/Simple-Game-Solutions.git`.

5. Click **OK**.

#### 1.3.2. MacOS, Linux, Unix

Use the package manager provided by your OS distribution to install GIT. Then clone the repository to a directory of your choice:

1. Open a terminal and change to a folder of your choice (e.g., your home directory):  
   `cd ~`

2. Clone the repository:  
   `git clone https://github.com/AmigaMaster/Simple-Game-Solutions.git`

## 5. Documentation

This section provides background information, tips, and guidelines if you are interested in contributing to Simple Game Solutions.

### 5.1. How It Started

Simple Game Solutions was born in late 2019 out of frustration over the difficulty of finding written guides or hints, particularly for fan-made and rare games. Let's take a brief look at modern game guides without dismissing them—they all serve a purpose for specific audiences.

**Let's Plays / Longplays**  
If you cannot find a readable solution, a video Let's Play or Longplay is often available. But let's be honest: Why watch someone else play a game when you want to experience it yourself?

Skipping through a video to find a specific puzzle solution can be tedious, especially in non-linear games. Furthermore, most Let's Plays are split across numerous short clips.

**Game Guides and Walkthroughs**  
These vary greatly in size and complexity. While some are exceptionally well-written (such as official strategy guides), they often reveal too much of the game's plot.

Online guides tend to be split across multiple separate pages, likely to generate site and ad clicks — which is understandable from a website owner's perspective.

While vastly superior to videos, jumping between pages is still inconvenient compared to a single, comprehensive text document. Additionally, web guides often include images that may accidentally spoil the experience.

**Message Boards**  
An excellent option for specific questions. However, depending on the game's popularity and community activity, getting a reply can take time, and getting stuck multiple times means having to ask repeatedly.

Message boards almost always require user registration to post.

**Hint Systems**  
Hint systems provide gradual clues—ranging from vague hints to the exact solution—split across different levels.

The most prominent example is the [Universal Hint System (UHS)](http://www.uhs-hints.com), which was specifically designed for this purpose from the ground up.

However, using the UHS format for a complete traditional walkthrough is cumbersome. Writing content requires a Windows-only UHS editor, there is no open web interface for hint files, and all publications require manual approval by the UHS developers—making it unsuitable for our open workflow.

An open-source implementation of the UHS reader is available at [OpenUHS](http://freshmeat.sourceforge.net/projects/openuhs).

### 5.2. Philosophy of Simple Game Solutions

The core principles behind this project:

#### 5.2.1. File Format

Technology changes rapidly, but text-based files remain universally accessible without requiring specialized tools or software.

By using Markdown as a markup language, text files can be rendered into attractive output formats while retaining readability in plain text form. Markdown is designed to be as easy to read and write as possible, building on established text conventions.

Above all, readability comes first: a Markdown file should always be fully readable in a raw text view.

#### 5.2.2. It is for the Player

Focus on what is essential for the player. Let the game tell its story—narrative recaps do not belong in a solution. If you wish to share personal thoughts, add an addendum at the very end of the file. During gameplay, allow players to make their own discoveries and assumptions.

Let players decide whether they just need a quick nudge because they are stuck or prefer a full walkthrough to experience the story without puzzle frustration.

## 6. Writing and Contributing a Solution

Things to keep in mind when writing your own solutions.

### 6.1. Text Editor Recommendation

If you already have a favorite text editor, stick with it. If you are looking for a versatile, all-in-one editor, we recommend [Visual Studio Code](https://code.visualstudio.com/), available for Linux, macOS, and Windows. It features built-in support for web-based languages, including Markdown, and its extension ecosystem allows you to add custom features and Git integration effortlessly.

For Markdown editing, we recommend these extensions:

  [Markdown All in One](https://marketplace.visualstudio.com/items?itemName=yzhang.markdown-all-in-one)  

  [markdownlint](https://marketplace.visualstudio.com/items?itemName=DavidAnson.vscode-markdownlint)

### 6.2. Learn using Markdown (Optional)

If you want to incorporate text formatting or headers, check out a Markdown guide such as [GitHub Markdown Guides](https://guides.github.com/features/mastering-markdown/). Alternatively, open any existing `.md` file in the Simple-Game-Solutions repository and click the `Raw` button to inspect how Markdown looks in plain text.

*Markdown is very easy to learn*—even GitHub-flavored Markdown features fewer than a dozen basic elements.

If you prefer **not** to use Markdown, a standard plain text file works perfectly fine.

### 6.3. Keep the Content Simple

You do not need to over-explain actions. Focus strictly on complex or ambiguous interactions using simple command phrases:

- WALK TO edge of the cliff
- USE flashlight with darkness

**Avoid overly descriptive phrasing:**

- After exiting the car, walk to the edge of the cliff
- Inserting the battery enables you to use the flashlight with the darkness

### 6.4. Keep Layout and Formatting Simple and Consistent

Files must always remain easily readable in plain text form. The only exception is when text alone cannot adequately describe something (e.g., some picture puzzles).

If you establish a specific style for certain elements (such as highlighting inventory items), maintain that style consistently throughout the document.

### 6.5. Single Text File

Write your walkthrough in a single text file. While the solution can reference external assets (such as images for maps, puzzles, or save games), the core guide itself must not be split across multiple text documents.

This preserves seamless searchability without requiring you to open multiple files.

### 6.6. Choose a File Name and Extension

Use the following naming convention:

`[Game Title]-(Description)-(Language code).[extension]`

**Game Title:**  
Required: Yes

Use the complete game title where possible.

**Description:**  
Required: No

An optional parameter used only when attaching auxiliary files like maps or puzzle graphics. Use short descriptive labels such as `map_mars` or `puzzle_stonedisc`.

**Language Code:**  
Required: Only if the file is language-dependent.

Omit this code if the content is language-independent. Currently, we have the following languages in our solutions:

| Code | Language |
| ---- | -------- |
| DE   | German   |
| EN   | English  |

More languages codes can be found on [ISDCF](https://www.isdcf.com/registry/languages)

**Extension:**  
Please use `.md` for Markdown files or `.txt` for plain text files.

**File Name Examples:**

``` text
Indiana Jones and the Fate of Atlantis-EN.md
The Longest Journey-DE.md
Zak McKracken and the Alien Mindbenders-EN.txt
Zak McKracken and the Alien Mindbenders-map_mars.png
```

## 7. Tips and Tricks

Tips gathered from writing initial solutions to ensure Markdown formatting remains plain-text friendly:

### 7.1. Inserting Web Links

Always prioritize readability in plain text view.

**Inline Links**  
For simple links like [Google](https://google.com), use standard inline linking. In plain text files, you can also paste URLs directly.

*This remains easily readable in text form:*

``` Markdown
For simple links like [Google](https://google.com), use standard inline linking. In plain text files, you can also paste URLs directly.
```

**Reference Links**  
If your text becomes cluttered due to multiple or long links (e.g., [Google], [Yahoo], [MSN]), use *reference links*:

  [google]: https://google.com        "Google Search"
  [yahoo]:  https://search.yahoo.com  "Yahoo Search"
  [msn]:    https://search.msn.com    "MSN Search"

*Clean and readable in text form:*

``` Markdown
If your text becomes cluttered due to multiple or long links (e.g., [Google], [Yahoo], [MSN]), use *reference links*:

  [google]: https://google.com        "Google Search"
  [yahoo]:  https://search.yahoo.com  "Yahoo Search"
  [msn]:    https://search.msn.com    "MSN Search"
```

### 7.2. Highlighting Elements using Unicode Symbols

You can use Unicode characters to add symbols and color to your text. However, please consider the following guidelines:

1. Prefer standard ASCII  
   The safest approach to guarantee absolute readability in plain text is to stick to standard ANSI letters and numbers.  
   > **Note:** Older or restricted environments do not or dot not fully support certain Unicode characters, often rendering them as placeholder boxes.

2. Use sparingly  
   Unicode requires UTF-8 encoding. Some older editors do not fully support UTF-8 and may display corrupted fallback characters instead (e.g., displaying a red circle as `ðŸ”´`).

3. Always combine with native text formatting  
   Some viewers do not support colors, causing Unicode symbols to appear monochrome. Always pair them with native Markdown elements like `embedded code`, *italics*, or **bold text**.
   > You can also use quotes, but they require a new line and cannot be displayed inline.

Short table of usable Unicode characters:

| Rendered  | Source Code | Native | Name       |
| :-------: | ----------- | :----: | ---------- |
| &#x2757;  | `&#x2757;`  |   ❗    | Attention  |
| &#x1F534; | `&#x1F534;` |   🔴   | Red circle |

**Example:**

------------------------------------------------------------

> ❗ **WARNING:** Save your game here!  
>   You will die if you make a mistake.

------------------------------------------------------------

This is still perfectly readable in raw text view:

``` Markdown
> ❗ **WARNING:** Save your game here!  
>   You will die if you make a mistake.
```

A complete list of Unicode emojis and symbols can be found at the [Unicode Emoji Chart](http://www.unicode.org/emoji/charts/full-emoji-list.html).

### 7.3. Spoilers

Standard Markdown does not have a native spoiler element. A lightweight HTML solution can achieve this while keeping the source relatively readable. Always include a clear warning label before spoilers.

Example:

------------------------------------------------------------

<details><summary>
*** SPOILER AHEAD *** Click to reveal content
</summary>
Note that Markdown syntax does not render inside HTML tags, meaning **bold text** will not work directly.<br>
Use basic HTML formatting inside spoiler tags instead and keep it to a minimum.
</details>

------------------------------------------------------------
